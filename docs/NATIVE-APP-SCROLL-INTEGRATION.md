# Production-App native scroll integration

This closes a narrower gate than desktop parity: running the actual production App view, update, receive, direct restoration operation and native `on_scroll` feedback against the rebuilt Iced widget tree. Prior [reader-anchor evidence](<NATIVE-READER-ANCHORS.md>) proved the pure/model layer and a standalone native operation separately; it did not execute their integration.

## Opt-in public rig

The [feature-only rig](<../app/src/scroll_fixture.rs>) is enabled by `public-layout-fixture` and embeds the production App without its subscription, worker start, Node, Host, account services or business-effect executor. It installs only PUBLIC synthetic snapshot/page/decision metadata and retains a test command receiver. Any queued command fails qualification and is dropped, never executed or serialized. The [native example](<../app/examples/scroll_app_smoke.rs>) runs returned App Tasks and forwards real `Scrolled`/`ScrollApplied` messages, unlike the paint-only layout fixture. Unsolicited button/editor/business messages are ignored before calling App update.

Fixture-only IDs on actual outer raw-row containers permit a read-only widget operation to observe durable key112's real slot bounds. They do not add wrappers or alter geometry and are excluded from the default production build. Pinned Iced traverses untranslated child layout bounds, so actual viewport-relative slot top is `row.y - viewport.y - scroll_translation.y`, expected `-12px`. This observation is independent of the model's prefix sum, but not an independent proof of text clipping, glyph rendering or user-input semantics.

## Scripted phases

1. After the owned native window opens, establish one scripted PUBLIC reader position at raw key112/intra12 in eighty rows100–179, rotate the geometry revision and execute production positioning. The initial real widget/model starts at zero; this is not restoring saved production startup state.
2. Reflow a controlled application frame1040×800→650×800 inside the same owned native window, then execute production reflow against the rebuilt actual widget. PUBLIC words are calibrated to genuinely change native row heights/prefix, not merely an operation ID. This does **not** qualify native window-manager resize negotiation: fixed Wayland bounds prevented the requested resize, while a resizable window was tiled to1280×1410. No compositor/desktop settings are changed to force a test result.
3. Deliver twelve older PUBLIC rows88–99 through the actual Page receive path, preserving key112/intra12 in92 rows. This is no page request, transport/RPC or Host ACK.
4. Deliver a PUBLIC approval Waterfall and open it locally. Transcript operations/row containers are absent while hidden; no reply or approval effect is submitted.
5. Deliver the corresponding worker-shaped Root Cancel through actual App receive. Its remount restores the same reader identity via the real rebuilt native scrollable.

Each active phase advances from a current stamped operation receipt and immediate native read-only observation. Scroll notifications are processed but are not required completion receipts. No delayed restoration or sleep-based model synchronization is used. The owned window has a separate20s deadline; an optional250ms final screenshot grace affects paint only. Exactly one accepted operation receipt is expected in each active phase and none while hidden. Generation/revision/feedback IDs must change appropriately. All geometry/model/native comparisons allow at most1px for pinned native rounding.

## Viewport-only feedback refinement

Pinned Iced can emit scroll notifications on redraw after viewport/content bounds change without user input. A variable-height composer/footer or warning can therefore enter/leave the98% follow threshold without a wheel movement. The production observer now treats changed viewport height with the previous offset's legal native clamp as geometry-only, retaining follow intent and feedback serial; differing displacement still supersedes old operations. Three model-only regressions cover entering/leaving the end threshold, a clamp, and differing input.

This is a local hint, not notification provenance. Content-only changes or simultaneous geometry/input can remain ambiguous. Retaining following intent alone does not independently prove that every arbitrary footer change immediately snaps the visual end; ordinary follow-positioning remains separate.

The subsequent [native history performance qualification](<NATIVE-HISTORY-PERFORMANCE.md>) extends this same actual-App driver with bounded `--rows`, `--cycles`, post-operation `--idle-ms` and private `--phase-log` metadata.
