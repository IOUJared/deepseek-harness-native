# Native timed-question transport ownership

## Scope

The native transport provides an acquired `QuestionClaim`. The application **still refuses timed questions**: no native claim coordinator, timed answer channel, timer or continued-question control is enabled. This reference describes the transport capability and exact audited alpha behavior, not completed desktop parity or live native timed-question qualification. The previously delivered development archive remains its earlier immutable snapshot.

[Live-decision ownership](<NATIVE-DECISION-OWNERSHIP.md>) now independently checks worker-issued tickets, supported request/answer semantics and exact actor-intake delivery instances. Its delivery token retires on reply ACK and is **not** a timed lease; the separate question claim must still survive that acknowledgement. Both worker and UI continue refusing timed replies.

## Host behavior and authority

A foreground request is an ordinary question batch with optional `wait: {callId, timed?: boolean}`. There is no public `timedWait`, native deadline or projection lease field. Actual timed requests set `timed: true`; indefinite requests can carry only `callId`. The tool's timeout is seconds, not a client countdown source. See [request types](<../../deepseek-harness-linux/packages/interaction/user-questions/src/types.ts#L128-L145>) and [timed tool](<../../deepseek-harness-linux/packages/interaction/tool-ask-user/src/timed.ts#L191-L204>).

`userQuestions/attachWait` is a mux **stream** addressed by explicit live root Agent and call ID. The Host rejects unregistered/exact-instance mismatches and delegated callers; attachment is keyed by the Agent instance, not merely durable question metadata. Although this alpha Host internally shares its Agent/session ID string, the native `AgentId` and `SessionId` remain deliberately distinct. Take the actual Agent ID from a current runtime event; selected session rows, persisted lineage and `agentAvailable` cannot manufacture it. See [Host root checks](<../../deepseek-harness-linux/packages/interaction/user-questions/src/index.ts#L131-L148>), [Host attach](<../../deepseek-harness-linux/packages/interaction/user-questions/src/index.ts#L208-L220>), [native ID types](<../transport/src/dto.rs#L1-L42>).

The generator inserts a nonexclusive claim **when its first iteration runs**, disables the unattended timer and yields exactly one `{remainingMs: max(0, originalHostDeadline - HostNow)}`. Its next iteration waits for termination. Constructing a stream/sending mux open is not claim acquisition. Any existing claim keeps the wait open past the absolute Host deadline; a sibling can validly acquire an opening value of zero. The deadline is **not extended or rebased**. Removing the last claim resumes expiry at the original deadline, immediately if overdue. Business stream cancellation, disconnect, consumer return or Host closure releases it. [Actual implementation](<../../deepseek-harness-linux/packages/interaction/user-questions/src/timed-wait.ts#L33-L82>) owns these semantics.

A successful reply RPC retires only this client's delivery. It may acknowledge an idempotent no-op after another client won; it is not accepted-answer/tool-success proof. The replying client gets no self-Cancel. The browser therefore holds its claim through Host stream termination **after local settlement**, not only until reply enqueue or acknowledgement. Normal claim end carries no answered/expired/aborted/continued reason. See [browser claim lifecycle](<../../deepseek-harness-linux/packages/client/ui-user-questions/src/client/index.ts#L219-L274>), [Gateway first-result behavior](<../../deepseek-harness-linux/packages/api/gateway/src/index.ts#L614-L667>) and [native reply acknowledgement](<../transport/src/http.rs#L610-L642>).

## Native API

`Mux::hold_question(&AgentId, &ToolCallId)` covers queue/socket transmission and first-item intake with one configured transport timeout. Interrupted/timed-out acquisition drops its stream owner, requesting local cancellation with late-frame retirement. It never answers, rejects or delegates. End before the first item produces fixed `Error::QuestionUnavailable`, not guessed business expiry. A malformed item is `InvalidDto`; remote failure, lifetime loss, correlation or overload retains its fixed transport diagnosis.

The question stream requires one JSON object containing only an unsigned-integer `remainingMs`; missing/extra fields, arrays, wrong types, negative/fractional/overflow values and second items fail closed. A valid zero value does not expire locally. The acquired `QuestionClaim` is non-Clone/non-serializable with no private socket/cookie accessor. Its opening-duration getter is an **initial sample**, not renewed TTL, running countdown, current remaining time or exclusive answer authority. There is no automatic timer, heartbeat, polling, retry or reply.

`wait_closed(&mut self)` actively waits for Host stream end without a new answer deadline. Abandoning that read preserves the claim and allows polling it again. Terminal `Ok(())`/fixed error is sticky, even if the generation closes later. Closure of a still-live generation/mux yields a fixed error. A first item can have an end immediately buffered behind it; monitor closure and the actual delivery **before enabling answers**, not simply because acquisition returned successfully.

`release(self).await` consumes and locally unsubscribes; Drop requests the same unsubscribe. Neither is a Host release ACK, question rejection or Turn cancellation. Generation close also awaits the mux actor. A last-claim release may let original Host expiry win immediately. Retain the owner through uncertain reply failure and eventual Host settlement or definite teardown; no rollback/reclaim/retry is inferred. Callers must independently fence transport generation, actual Agent/call, delivery event, UI/operation lifetime and settlement; the capability does not discover or enforce their application association.

Development API additions: exported `QuestionClaim`, `Mux::hold_question`, and `Error::QuestionUnavailable` (exhaustive external matches need updating). The existing low-level `question_wait` remains available, but opening transmission alone is not a grant and question items now receive strict single-frame validation. [Implementation](<../transport/src/question.rs>) and [mux](<../transport/src/mux.rs>) are authoritative.

## Verification and remaining work

[Parent verification record](<../app/evidence/question-claim-foundation-01/verification.json>) records exact implementation/test SHA256 identities, 73 transport behavior tests plus four privacy doctests, eight actual alpha wait component tests, all-target native consumer compilation and 12 focused interaction regressions. No full app test run, rebuilt release archive or graphical/native-input qualification is asserted.

[Fake-wire integration tests](<../transport/tests/support/question_claim.rs>) use the actual authenticated native transport against an isolated local Node protocol fixture. They check metadata-only frames, exact explicit Agent/call arguments, zero/nonzero samples, acquisition/end/error distinctions, malformed/duplicate frames, sticky terminals, abandoned acquisition/reads, opening timeout and late-frame retirement, stream limits, sibling preservation, Drop/release and independent ACK/end order. Fixture-only `session/cancel` is an explicit scripted end barrier; **the claim API never sends it**. These are not a complete Gateway/registered-Agent/Host question composition.

[Focused alpha Host component tests](<../../deepseek-harness-linux/packages/interaction/user-questions/tests/timed-wait.spec.ts>) exercise the real wait implementation under owned fake timers: unattended expiry, claim retention past deadline, original-deadline resumption, generator return, parent cancellation, no claim before iteration, and zero-duration sibling acquisition. They do not instantiate a real question/Agent/model composition. Queue-inclusive acquisition budgeting is source-reviewed; the wire timeout test delays the first item after open, not a controlled pre-send queue stall. That distinct empirical race remains a test gap.

Native worker/UI integration remains required: validated timed-request admission, current explicit authority, bounded independent claim ownership, acquire/terminal/delivery/answer races, no silent release on hide/local submit, honest uncertain outcome handling, actual isolated keyless delivery/reply/Host-settlement tests and physical input/paint. If a countdown is implemented, use only received duration with checked monotonic arithmetic and preserve focus/edit/hide policy; never reconstruct from tool timeout, persisted history or wall clocks.

Continued questions require a separately validated `userQuestions` projection and inbox state plus current Agent binding. The projection carries call/questions/state, **not Agent authority/deadline/lease**. `answer_continued` true means queued, not admitted; false means no longer continued, and errors/timeout may be uncertain. Reconcile queue discard/admission with projection removal rather than treating ACK as completion. There is no continued Cancel endpoint. No automatic selection/skip/approval/answer/delegation/provider call is added here.
